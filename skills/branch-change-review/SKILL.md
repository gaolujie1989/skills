# 分支变更评审

## 目标

帮助人工 reviewer 判断每个代码文件中每处实质改动是否合理。既解释跨文件的端到端实现，也提供无遗漏的逐文件改动台账；不代替人工批准设计。

## 输入与范围

确认需求目标、实现 Plan、base branch 或 base commit，并列出来源。缺失时，先从任务与计划文件、需求或架构文档、README、分支名、commit、测试和代码中查找候选内容，概括后请用户确认。只有用户明确允许时，才仅根据代码推断需求或 Plan。

使用 merge base 分析完整分支差异，并单独说明 staged、unstaged 和 untracked 变更。

## 工作流程

1. 确定需求、Plan、base、merge base 和变更范围。
2. 检查提交、完整 diff 及必要的基准版本和当前代码。
3. 按业务行为或职责建立逻辑变更组，追踪入口、核心逻辑、数据与副作用、响应和测试。
4. 将实现与需求和 Plan 对照，并建立逐文件改动台账。
5. 将台账与完整文件列表和 diff hunk 核对，再判断目标偏离、范围膨胀和不必要复杂度。

## 逐位置分析规则

覆盖每个代码文件和独立实质改动位置。代码文件包括源代码、测试、配置、迁移、构建文件和脚本。

严格区分：

- **目标**：改动希望产生的具体行为、能力或结构结果。
- **原因**：为实现目标，此处为何必须或值得修改，包括约束、缺口、依赖或权衡。

逐项检查 diff hunk：

- 用符号、配置项、测试名或 hunk 定位，必要时补充行号。
- 同一文件中目标或原因不同的改动分别列项；只有两者完全相同的相邻改动才可合并。
- 新文件按关键职责或符号拆分；删除说明成立依据和调用方处理；搬迁区分位置变化与行为变化。
- 合并标记生成、格式化等机械变更，并说明来源；明确列出二进制或无法读取的变更。

将原因标记为：

- **明确记录**：需求、Plan、ADR、注释或 commit 已说明。
- **根据实现推断**：由代码、测试或调用关系推断。
- **无法确认**：证据不足，需人工确认。

不要用“为了实现需求”“配合其他修改”或“优化代码”代替具体因果关系，不要把推断当作作者意图。评估设计时关注必要性、放置层次、简单替代、收益、成本和风险；不要仅因文件、层级或接口数量判定过度设计。

## 输出

### 1. 范围与结论

说明审查范围和信息来源；概括分支目标、实际能力、实现策略、需求与 Plan 的已实现项、遗漏、超范围和方案差异；汇总主要合理性判断与待确认问题。

### 2. 逻辑变更地图

按逻辑变更组说明目的、修改前后行为、实现路径、关键文件和符号、设计选择与依据、测试证明和人工判断点。

### 3. 逐文件改动台账

按路径列出全部代码文件。先说明文件职责及其在方案中的角色，再为每个独立改动位置列出：

- **位置与改动**
- **目标**
- **原因及依据等级**
- **合理性判断材料**：必要性、层次、简单替代、风险或待确认前提
- **关联**：所属逻辑变更组及相关改动

不要用文件级摘要代替逐位置说明，使人工能够独立接受或质疑每一项改动。

### 4. 覆盖核对

列出全部变更文件并标记为已解释、非代码、机械或生成、无法读取。明确是否仍有未解释的代码 hunk；若有，列出位置和原因，不得声称已完整评审。

## 边界

保持只读，不修改代码、运行修复、stage、commit、更新需求或创建永久评审文档。可提示明显 bug，但将系统性的缺陷、回归、安全和测试遗漏评审交给 Codex 原生 `/review`。
