# 分支变更评审

## 目标

帮助人工 reviewer 理解整个分支，而不是代替人工批准设计。重点回答：

* 需求目标是什么；
* 实际改了什么；
* 功能如何端到端实现；
* 为什么可能采用当前方案；
* 实现是否偏离目标或 Plan；
* 是否存在范围膨胀、提前抽象或不必要复杂度。

## 开始前确认

正式分析前必须确认：

1. 需求目标；
2. 实现 Plan；
3. base branch 或 base commit。

用户已提供时直接使用，并明确列出来源。

缺少需求或 Plan 时，先在仓库中查找：

* 任务或计划文件；
* 需求、架构和 ADR 文档；
* README；
* 分支名和 commit message；
* 测试、注释及相关代码。

找到候选内容后，先向用户概括：

* 推测的需求目标；
* 候选 Plan；
* 准备使用的 base；
* 尚缺少的信息。

得到用户确认后再正式分析。找不到可靠内容时，向用户索要。只有用户明确允许时，才可仅根据代码推断。

## 分析规则

使用 merge base 分析完整分支差异，同时单独说明 staged、unstaged 和 untracked 变更。

不要只逐文件总结。按业务行为或职责建立逻辑变更组，例如：

* 新增订单提交流程；
* 增加权限控制；
* 修改 API；
* 增加审计；
* 重构共用校验。

必要时同时阅读 base 和当前分支代码，并追踪：

```text
入口
→ 参数校验
→ Service / Use Case
→ Model / Domain
→ 数据库和副作用
→ 响应
→ 测试
```

分析设计选择时，说明：

* 选择了什么方案；
* 解决什么现实问题；
* 带来什么收益和成本；
* 是否存在更简单方案；
* 哪些前提需要人工确认。

所有原因必须标记为：

* **明确记录**：需求、Plan、ADR、注释或提交中明确说明；
* **根据实现推断**：由代码、测试和调用关系推断；
* **无法确认**：缺少足够依据。

不得把推断描述成作者真实意图，也不得仅因文件多、层级多或存在接口就判定过度设计。

## 输出结构

### 1. 审查范围

分支、base、merge base、commit 范围、未提交变更、需求和 Plan 来源。

### 2. 整体摘要

说明分支解决的问题、最终实现的能力、总体实现策略和重要架构影响。

### 3. 需求与 Plan 对照

列出已实现、未实现、超出范围及实际方案与 Plan 的差异。

### 4. 逻辑变更地图

每组说明：

* 目的；
* 修改前后行为；
* 实现路径；
* 关键文件和符号；
* 设计选择及依据；
* 测试证明的行为；
* 人工需要判断的问题。

### 5. 设计评审材料

分别列出：

* 与目标一致的设计；
* 可能的目标偏离；
* 可能的范围膨胀；
* 可能的不必要复杂度；
* 当前复杂度的实际收益；
* 可行的简单方案；
* 成本较高或不可逆的决策；
* 需要作者解释的问题。

### 6. 建议阅读顺序

按行为给出关键文件和符号的阅读路径，说明每一步应理解什么。

## 边界

默认只读。不得修改代码、运行修复、stage、commit、更新需求或创建永久评审文档。

明显 bug 可以顺带提示，但缺陷、回归、安全和测试遗漏应主要交给 Codex 原生 `/review`。
