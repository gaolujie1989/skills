# 审查需求与设计

对已完成的**需求文档 + 系统设计**进行第二轮 brainstorming。

目标不是重新设计，而是主动寻找遗漏、冲突、不明确和不合理之处，并最终完善现有文档。

## 1. 审查需求

先只关注业务需求，不受现有设计限制。

完整阅读需求，结合具体业务场景检查：

* 是否遗漏业务规则、条件、例外和边界场景
* 不同规则是否前后冲突
* 状态、角色、操作组合下是否存在未定义行为
* 是否存在多种合理解释
* 是否依赖未经确认的隐含假设

判断标准：

> 对一个合理业务场景，如果仅根据需求无法唯一确定系统应该如何处理，则视为潜在需求缺口。

发现需要业务决策的问题时，以 brainstorming 的方式**一次只问一个关键问题**，不要自行补充未知业务规则。

需求审查完成后，再进入设计审查。

## 2. 审查设计

基于已经确认的需求，整体审查数据库、API、Service 等系统设计。

重点检查：

* 每条重要需求是否都有对应设计
* 数据模型、API、Service 是否表达同一套业务规则
* 状态、约束、事务、并发、异常和副作用是否存在明显缺口
* 不同设计之间是否冲突
* 设计是否引入需求没有要求的行为或不必要复杂度

始终从：

`需求 → 数据库/API/Service`

以及反向：

`数据库/API/Service → 需求`

检查是否能够对应。

发现无法确定的设计问题时，同样一次只确认一个关键问题。

## 3. 整体修订

需求和设计审查全部完成后，再统一修改相关文档。

修改时同步处理所有受影响内容，避免只修一个位置造成新的不一致。

最后重新通读需求与设计，确认：

* 已发现的需求缺口均已处理
* 需求内部没有已知冲突
* 设计完整承接需求
* 各设计之间保持一致
* 没有未经确认地创造业务规则
* 没有明显违反 YAGNI 的设计

审查的目标不是让文档更复杂，而是让**需求明确、设计完整、两者一致**。
