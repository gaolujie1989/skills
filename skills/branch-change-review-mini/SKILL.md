# Branch Change Review

## 输入

- 目标分支，默认尝试识别仓库主开发分支
- 需求目标
- 实施计划或规格文档

## 工作流程

1. 确定比较基线。
2. 查找需求和计划。
3. 检查提交历史和完整 diff。
4. 按功能建立跨文件的逻辑变更组，解释端到端实现。
5. 逐个检查 diff 中的代码文件和 hunk，建立逐文件改动台账。
6. 将每处实质改动与需求、计划和逻辑变更组对应。
7. 核对台账与完整 diff，确认没有遗漏代码文件或独立改动位置。
8. 识别偏离目标、遗漏、复杂度和过度设计。

若缺少需求或计划，先在代码库中查找；找到候选内容后要求用户确认。

## 逐文件改动台账

按文件路径输出。先说明文件职责，再为每个目标或原因不同的改动位置分别列出：

- **位置**：符号、配置项、测试名或 diff hunk；
- **改了什么**：简述事实；
- **目标**：该处改动要产生的具体结果；
- **原因**：为何需要在这里这样改；
- **依据**：明确记录、根据实现推断或无法确认；
- **人工判断点**：必要性、放置层次、简单替代、风险或待确认前提；
- **关联**：所属逻辑变更组及相关文件。

不要用文件级摘要代替逐位置说明。同一文件中目标或原因不同的改动必须拆开；只有目标和原因完全相同的相邻 hunk 才可合并。生成、格式化、重命名、删除或不可读变更也要列出并标记。

“为了实现需求”“配合其他修改”“优化代码”不是充分原因。说明具体的约束、缺口或调用关系；无法证明作者意图时写“无法确认”，不要把推断当作事实。

最后列出全部变更文件的覆盖状态，并明确是否仍有未解释的代码 hunk。
