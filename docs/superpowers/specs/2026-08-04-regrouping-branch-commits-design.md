# 分支提交重组技能设计

## 背景与目标

新增 `regrouping-branch-commits` 技能，用于将一个已有线性提交历史的功能分支，依据需求或 Plan 从其与基准分支的分叉点重新构造成阶段性提交。重组在新分支进行，原分支作为不可变的恢复锚点保留。

技能的成功标准是：新提交序列能清晰对应需求阶段，每个提交尽可能独立构建和验证，且新分支最终文件树与原分支 tip 完全一致。

## 范围

第一版支持：

- 当前分支是命名的 Git 功能分支；
- 工作区和索引完全干净；
- 从分叉点到原分支 tip 的提交历史为线性历史；
- 依据明确需求、Plan 或经用户确认的行为增量跨原提交、文件和 hunk 重新分组；
- 在新分支创建全新的提交序列，同时保留原分支。

第一版不支持：

- 自动处理 staged、unstaged、untracked 或 ignored 的本地改动；
- 自动扁平化或重建 merge commit；
- 保留原提交的 OID、作者日期、签名或拓扑；
- 自动 stash、force-push、push、删除分支或替换原分支；
- 仅通过 interactive rebase 对原提交做 squash、reword 或 reorder。

## 技能形态

技能采用与仓库现有技能一致的单文件结构：

```text
regrouping-branch-commits/
└── SKILL.md
```

`SKILL.md` 使用中文正文；名称和触发描述覆盖 `merge-base`、重组提交、阶段性提交、保留原分支等检索词。第一版不提供脚本、引用资料或资产。需求理解、hunk 归类和安全确认依赖上下文判断，隐藏在固定脚本中的自动化会削弱可审查性。

## 术语与输入

- **原分支**：待重组的功能分支，整个流程中其 ref 必须保持不变。
- **base**：用户指定或由仓库默认分支推断、再经用户确认的基准分支。
- **fork**：`base` 与原分支的标准 `merge-base`，确认后固定为完整 OID。
- **原 tip**：执行前原分支指向的完整 commit OID。
- **目标分支**：承载新提交序列的新分支，其名称必须由用户确认且尚不存在。
- **阶段**：对应需求或 Plan 的一个逻辑完整、按依赖排序且尽可能可独立验证的行为增量。

必需输入包括需求目标、Plan（如有）、base 或其确认结果、目标分支名，以及仓库适用的构建和测试命令。若需求或 Plan 未直接提供，技能先从仓库文档、任务文件、提交和测试中寻找候选内容，标明来源并请求用户确认。根据代码作出的推断不能冒充已确认需求。

## 安全契约

### 修改前门槛

技能必须在任何 Git 状态修改之前确认：

1. 当前位于命名分支，且该分支是待重组的原分支；
2. staged、unstaged 和 untracked 均为空；
3. 没有进行中的 merge、rebase、cherry-pick、revert 或 bisect；
4. base、fork、原 tip 和原 tip tree 均已记录为完整 OID；
5. 标准 merge-base 唯一，且用户已确认该 fork；不得擅自用同名 upstream 或 `merge-base --fork-point` 代替；
6. `fork..原 tip` 不包含 merge commit；
7. 目标分支不存在；
8. 用户已一次性确认完整分组方案、目标分支名和安全快照。

任何条件不满足都必须停止，不得尝试自动修复或绕过。

### 不变量

- 原分支 ref 在流程开始、每个关键阶段和完成时都必须等于原 tip。
- 只有目标分支允许执行 reset 和 commit。
- 不得执行 `reset --hard`、stash、clean、force-push 或自动 push。
- 最终 `目标分支 HEAD^{tree}` 必须等于 `原 tip^{tree}`。
- 任何失败都保留现场；不得自动 reset、clean、删分支或切回原分支。

## 只读分析与分组计划

技能在创建目标分支之前完成以下工作：

1. 收集需求、Plan、仓库提交风格和验证命令，并记录信息来源。
2. 确认 base、fork 和原 tip，检查 `fork..原 tip` 的提交历史及完整 diff。
3. 建立改动台账，覆盖新增、修改、删除、重命名、文件模式、二进制、生成文件及每个独立实质 hunk。
4. 优先采用需求或 Plan 已定义的阶段；没有明确阶段时，按可独立理解、尽可能可独立验证且依赖顺序合理的行为增量推导。
5. 将每项改动恰好分配给一个阶段。共享文件按 hunk 拆分，不允许遗漏或重复归类。
6. 将阶段按依赖排序，并与完整 diff 反向核对覆盖率。

每个阶段的计划必须包含：

- 阶段目标及对应需求；
- 前置依赖；
- 纳入的路径和 hunk；
- 明确排除项；
- 符合仓库风格的 commit message；
- 最低充分的阶段验证命令；
- 无法自动拆分或需要人工判断的内容。

计划还必须展示原分支、base、fork、原 tip、原 tip tree 和目标分支名。用户一次确认完整计划后，技能才能进入修改阶段。

## 执行流程

1. 再次运行全部前置检查，并确认记录的 OID 和分支 ref 未变化。
2. 从原 tip 创建并切换到目标分支。
3. 仅在目标分支执行 `git reset --mixed <fork-oid>`。
4. 将 reset 后的 staged、unstaged 和 untracked 状态与改动台账核对。原 tip 中的新增文件在 mixed reset 后可能成为 untracked，甚至受 fork 状态下的 ignore 规则影响，因此台账必须以 `fork..原 tip` 的完整 diff 为准，而不能只依赖 `git status`。不一致时停止。
5. 按计划顺序逐阶段执行：
   - 只 stage 该阶段允许的路径或经审阅的 hunk；禁止无边界的 `git add .` 或全局 `git add -A`；
   - 对删除、重命名、文件模式和原 tip 中已跟踪但 reset 后被忽略的新增文件，依据台账显式处理；只有台账证明该文件属于原 tip 时才允许强制加入；
   - 核对 staged diff 与阶段清单完全一致，并运行 `git diff --cached --check`；
   - 创建 commit，再核对实际 commit diff 与阶段清单；
   - 在隔离的干净 worktree 中检出该 commit，运行阶段验证，避免工作区中后续未提交改动污染测试结果；
   - 阶段验证通过后才继续下一阶段。
6. 全部阶段完成后执行最终验收并输出报告。

## 最终验收

完成必须同时满足：

- 改动台账中的每项改动恰好被一个新提交消费；
- 目标分支没有 staged、unstaged 或 untracked 内容；
- 目标分支 `HEAD^{tree}` 与原 tip tree OID 完全一致；
- 原分支 ref 仍等于原 tip；
- 所有阶段验证通过；
- 在目标分支最终 commit 的干净 worktree 中运行的完整验证通过。

最终报告展示：安全快照、base 与 fork、原分支和目标分支、新提交序列、提交到需求的映射、逐阶段及完整验证结果、tree 等价性结果，以及未执行 push 的说明。

## 错误处理与恢复

- 修改前失败：报告不满足的门槛和只读证据，不创建目标分支。
- reset 后台账不一致：立即停止，报告目标分支、Git 状态、预期与实际差异；保留原分支恢复锚点。
- stage、commit hook 或阶段验证失败：停止后续阶段，报告已完成提交、失败步骤、当前 index/worktree 和剩余台账。
- 最终 tree 或完整验证失败：不得声称完成，不得 push 或自动清理。

失败报告只提供明确的恢复锚点和可选后续动作，不自动执行恢复。若用户决定放弃目标分支，必须先另行处理其中已完成提交和剩余工作区改动；不能用 hard reset 覆盖现场。

## 技能测试策略

技能按照 RED-GREEN-REFACTOR 验证：

1. **RED**：让未加载技能的独立代理处理至少三个组合压力场景，包括脏工作区、模糊 base、merge commit、目标分支冲突、测试失败和“直接改写更快”的时间压力，记录其不安全选择和理由。
2. **GREEN**：编写最小 `SKILL.md`，对相同场景复测，确认代理会在修改前停止、请求确认，或遵循新分支安全流程。
3. **REFACTOR**：针对新出现的绕过理由补充最小约束并复测，不加入未经场景证明需要的流程。
4. **端到端验证**：仅在一次性临时 Git 仓库中演练成功路径和失败路径，不在本仓库真实历史上试验重组操作。

端到端成功用例必须证明：

- 原分支 commit OID 始终不变；
- 目标分支从确认的 fork 重建，并按需求阶段生成提交；
- 阶段验证在不包含后续改动的干净 worktree 中运行；
- 最终 tree OID 与原 tip 完全一致；
- 技能没有 push、删除原分支或遗留未说明的 Git 状态。

负向用例分别覆盖脏工作区、进行中的 Git 操作、多个或错误的 merge-base、线性范围内存在 merge commit、目标分支已存在、阶段验证失败和最终 tree 不一致。每个用例都必须验证技能在正确边界停止且没有改动原分支。
